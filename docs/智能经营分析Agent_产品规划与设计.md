## 一、总体思路与三阶段规划总览

我建议在两者之间插入一个**"半自动沉淀与组合"**的过渡阶段，原因是——直接从"手动模板"跳到"完全自主"，跨度太大、风险太高，且会浪费第一步积累的结构化资产。三阶段如下：

| 阶段 | 核心命题 | 模板的角色 | Agent 的自主度 | 关键交付 |
|------|---------|-----------|---------------|---------|
| **Phase 1 · V1.0** 模板驱动 | 把报告思路固化成剧本，Agent 照本宣科 | 手动提炼的完整剧本 | 低：严格按模板步骤执行 | 可用的高保真分析报告 |
| **Phase 2 · V2.0** 半自动沉淀 | 模板规模化、可组合、可优化 | LLM 辅助抽取 + 人审；子模板可拼装 | 中：可按条件分支、组合多模板 | 模板规模 + 质量闭环 + 业务知识库 |
| **Phase 3 · V3.0** 自主规划 | 按问题动态规划，模板退化为技能库 | 作为 few-shot 技能被 RAG 召回参考 | 高：动态规划步骤、自验证、多轮深研 | 灵活自治的分析大脑 |

> **贯穿三阶段的"复用资产"（这是逐步完善、不推翻重来的关键）**
>
> - **数据查询清单**（工具层）：从 Phase 1 就是稳定底座，三阶段共享，只增不减。
> - **模板库**：Phase 1 手动剧本 → Phase 2 规模化/参数化/子模板化 → Phase 3 升格为"技能库/few-shot 语料"。
> - **执行引擎**：Phase 1 线性步骤执行 → Phase 2 条件分支执行 → Phase 3 动态规划执行（同一个引擎的泛化，不是另起炉灶）。
> - **执行日志/报告沉淀**：Phase 1 开始落库，Phase 2 用于评分优化，Phase 3 用于学习规划策略。

## 二、Phase 1 · 模板驱动分析 Agent（详细设计）

这是你要落地的第一步，也是资产沉淀的起点。下面给出完整设计，重点补全你点名的 **Agent 运行思路**。

### 2.1 四个核心组件

**① 模板库（template）—— 分析思路的"剧本"**

手动从现有经营分析报告中提炼。每个模板用自然语言描述完整思路，中间穿插对数据查询的调用，并显式记录引用了哪些查询。

**② 数据查询清单（data_query）—— 系统支持的取数工具**

这是受控的"语义层/工具层"。系统就支持这些查询，Agent 只能调用清单内的查询，不能自由写 SQL。这是准确性的根本保障。

**③ 意图路由（intent router）—— 对话框入口的"前台"**

用户输入需求后，用 LLM 识别意图、匹配最合适的模板，并从自然语言中抽取模板所需的参数（时间范围、业务单元、对象等）。

**④ Agent 执行引擎（execution engine）—— 照剧本"演出"的核心**

载入选中模板，绑定参数，逐步执行：每步调用数据查询 → 把数据交给 LLM 按该步分析逻辑生成结论 → 累积上下文 → 最后综合各步结论生成报告。

### 2.2 数据模型（补全）

**模板库表 template**

```
id                     -- 主键
name                   -- 模板名称，如"月度经营复盘"
scenario_desc          -- 适用场景描述（供意图路由匹配）
intent_examples        -- 示例问法（JSON 数组），如 ["本月经营情况","月度复盘"]
params_schema          -- 参数定义 JSON：[{name,time_range,required},{name,business_unit}...]
playbook               -- 自然语言剧本全文（含对查询的引用标记）
steps                  -- 结构化步骤 JSON：见下方
referenced_query_ids   -- 引用的数据查询 ID 列表（冗余，便于统计/治理）
output_template        -- 报告结构模板（章节大纲）
version, status        -- 版本号、启用/停用
created_at, updated_at
```

**steps 字段结构（关键）：** 每个步骤是一个自洽的"取数→分析→结论"单元。

```json
[
  {
    "step_no": 1,
    "desc": "营收与成本概况",
    "data_query_ids": ["Q_monthly_revenue", "Q_monthly_cost"],
    "analysis_logic": "计算毛利率=(营收-成本)/营收；判断环比、同比变化方向与幅度；标记异常波动点",
    "expected_output": "毛利率趋势 + 异常点说明"
  },
  { "step_no": 2, ... }
]
```

### 2.3 意图路由设计

意图路由做两件事：**选模板** + **抽参数**。推荐两种实现，可分阶段升级：

- ** 简单版**：用 LLM 一次性完成——把所有模板的 `scenario_desc` + `intent_examples` 作为候选喂给 LLM，让它输出"选中模板ID + 参数JSON"。模板少时（<30个）足够好用。
- ** 进阶**：先对模板做向量化（embedding），用户 query 向量检索 Top-K 候选，再交给 LLM 精选 + 抽参。模板多了再上这层。

> **兜底设计：** 当没有任何模板置信度足够时，不要硬选。路由应反问澄清（"您是想看月度复盘还是单品分析？"）或回退到一个"通用经营概览"模板，避免错误模板导致整份报告跑偏。

### 2.4 Agent 执行引擎设计（重点补全）

这是你特别要求补充的部分。执行引擎本质是一个 **"模板解释器"**——模板是自然语言+结构化混合的"程序"，Agent 是解释执行的引擎。完整运行流程：

**步骤一：参数绑定**

意图路由抽出的参数（如 time_range=2026-06、business_unit=华东）绑定到模板的 `params_schema` 槽位。缺必填参数时反问用户补齐。

**步骤二：剧本解析**

把模板 `steps` 解析为有序步骤列表，每步知道要调哪些查询、分析逻辑是什么、期望产出什么。

**步骤三：逐步执行循环（核心）**

多策略：严格for 循环，reAct、Reflection

对第 i 步（i = 1..N）：

1. **取数**：按本步 `data_query_ids` 调用数据查询清单中的查询，传入绑定参数，拿到结构化数据。
2. **入上下文**：把返回数据（必要时做摘要/格式化以控制 token）连同前序步骤结论一起放入上下文。
3. **分析**：调用 LLM，输入"本步数据 + 本步 analysis_logic + 已有上下文"，要求按 expected_output 生成该步结论。**LLM 在这里只做分析与表达，不碰取数逻辑**——这是可控性的关键。
4. **异常处理**：取数失败→重试/降级到替代查询；返回空值→在结论中如实提示而非编造；结论与前序冲突→标记待综合阶段处理。

**步骤四：综合与输出**

N 步执行完，把各步结论按 `output_template` 章节大纲，交 LLM 综合成完整报告（含总体结论、分项、建议）。报告落库到 execution_log。

> **为什么这样设计可控、可信？**
>
> - **取数与推理分离**：数据来自确定性查询（无幻觉），LLM 只在"已知数据上做分析和写结论"，出错面大幅收窄。
> - **步骤可追溯**：每步结论都能回溯到"调了哪个查询、拿到什么数据、用了什么分析逻辑"——可解释、可审计。
> - **失败可定位**：哪一步取数失败、哪一步结论异常，一目了然，便于迭代模板。

### 2.5 Phase 1 交付物与验收

- 3 张 DB 表（template / data_query / execution_log）+ 模板与查询的录入/管理界面。
- 意图路由 + Agent 执行引擎 + 对话界面。
- 首批 5–10 个高频模板（从你现有报告提炼）+ 对应数据查询清单接入。
- 验收：用户对话输入 → 自动选模板、取数、生成报告，报告质量达到分析师可用的"初稿"水平。

## 三、Phase 2 · 半自动沉淀与组合分析

目标：让模板从"少量手工品"变成"规模化、可组合、持续优化的资产"，并为 Phase 3 的自治打地基。

### 3.1 四个增量能力

**① LLM 辅助模板抽取（人审）**

把新的经营分析报告喂给 LLM，自动抽取成候选模板（识别步骤、推断引用的查询、生成 analysis_logic），人工审核修订后入库。把"提炼"从纯手工变半自动，模板规模快速扩张。

**② 模板参数化与子模板化**

把通用片段（如"毛利率分析""Top-N 结构分析"）抽象为可复用子模板，主模板通过引用组合子模板。意图路由可为复杂需求拼装多个子模板。

**③ 模板质量闭环**

基于 execution_log 的反馈数据，给模板打分（准确率、用户满意度、取数成功率），低分模板进入优化队列；支持版本管理，A/B 验证改进。

**④ 业务知识库**

沉淀指标口径、业务术语（"爆款""滞销"的阈值定义）、口径映射。这是市场反复强调的"语义层"，既提升路由准确率，也供 Agent 分析时引用，避免口径歧义。

### 3.2 执行引擎的升级

同一引擎从"线性步骤"升级为 **"条件分支执行"**：步骤可带条件（如"若毛利率下降超5%则追加成本结构分析子模板"）。这是 Phase 3 动态规划的雏形——引擎不变，调度策略变强。

## 四、Phase 3 · 自主规划分析 Agent

目标：积累足够多后，Agent 能对清单外的新问题动态规划分析步骤，但仍受数据查询清单约束、有自验证兜底。**模板不再绑死执行，而是作为"技能/few-shot 参考"被召回。**

### 4.1 三个核心能力

- **动态规划**：收到问题后，Agent 先规划"要回答这个问题需要哪些分析步骤、每步取什么数"，而非套用某个固定模板。规划时通过 RAG 召回**最相关的历史模板作为 few-shot 参考**（这正是 Phase 1/2 模板库的复用方式）。
- **自验证 + 多轮深研**：每生成一步结论先自评质量，不足时自动追加分析步骤（类似 ThoughtSpot Spotter 3 的"评估自己的答案并追加分析"）。
- **工具边界与建议**：仍只能在数据查询清单内取数；当发现清单不足以回答时，不硬编造，而是向用户/管理员"建议新增查询"，形成清单的自我生长闭环。

> **关键：** Phase 3 不是抛弃模板，而是把模板库"降维"成 Agent 的经验库。模板里沉淀的"什么样的题该怎么解"成为 Agent 自主规划的 few-shot 语料——Phase 1/2 的每一份模板都在为这一刻喂养。

## 五、阶段衔接逻辑：为什么后阶段不会浪费前阶段

你明确要求"逐步完善，避免第二步完全不使用第一步的成功"。以下是逐项映射：

| 资产 | Phase 1 状态 | Phase 2 演进 | Phase 3 演进 | 是否复用 |
|------|------------|------------|------------|---------|
| 数据查询清单 | 建立底座 | 持续扩充 | 仍是唯一工具层 + 自我生长 | ✅ 全程复用 |
| 模板库 | 手动剧本 | 规模化/参数化/子模板 | 升格为技能库/few-shot 语料 | ✅ 升格复用 |
| 执行引擎 | 线性步骤 | 条件分支 | 动态规划（同引擎泛化） | ✅ 渐进增强 |
| 执行日志 | 落库 | 用于评分优化 | 用于学习规划策略 | ✅ 持续喂养 |
| 业务知识库 | — | 建立 | Agent 推理时的语义参照 | ✅ 跨阶段 |

> **一句话总结演进逻辑**
>
> 模板从"必须照搬的剧本" → "可组合的乐高" → "可供参考的经验"；引擎从"会念剧本" → "会按条件分支" → "会自己规划"；数据查询清单和日志贯穿始终。没有任何一个阶段推倒重来。

## 六、关键设计决策与风险

### 6.1 关键决策

- **不让 LLM 写 SQL，只调预定义查询**：牺牲一点灵活性，换取准确性与可控性。这是对抗市场头号痛点（幻觉/口径错乱）的根本取舍，也是我们区别于纯 ChatBI 的护城河。
- **模板采用"自然语言剧本 + 结构化 steps"混合形态**：纯自然语言难执行，纯结构化难表达分析逻辑。混合形态让 LLM 可解释执行，又保留分析师的表达力。
- **三阶段而非两阶段**：中间过渡阶段降低跳跃风险，让"自主化"有真实的资产和数据支撑，而非空中楼阁。

### 6.2 主要风险与对策

| 风险 | 对策 |
|------|------|
| 模板提炼质量参差，导致报告质量不稳 | Phase 2 的评分闭环 + 版本管理 + A/B；高质量模板前置审核 |
| 数据查询清单覆盖不足，路由命中后取不到数 | 清单缺口探测；路由兜底反问；Phase 3 的"建议新增查询"闭环 |
| 意图路由误匹配模板，整篇跑偏 | 置信度阈值 + 兜底澄清；Top-K 候选展示让用户确认 |
| LLM 在"分析"环节仍可能误读数据 | 关键结论做数值校验（如算出来的毛利率与数据交叉核对）；结论标注数据来源 |
| token 成本随步骤数/数据量上升 | 取数结果先摘要/聚合再入上下文；长报告分段综合 |

### 七、待办

1、交互设计轻量化
